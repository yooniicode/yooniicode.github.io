DB 한 대로 버티기 힘들어지면 순서대로 작업하는 것이 일반적이다.

- 쿼리, 인덱스 튜닝
- 스케일 업 (더 큰 인스턴스로 교체)
- 레플리케이션 (읽기 분산)
- 샤딩 (데이터 자체를 쪼갬)

뒤로 갈수록 효과도 크고 비용도 커지는 특징이 있다.

레플리케이션과 샤딩을 개념 위주로 정리하고, 국내 기술블로그에 올라온 적용 사례를 참고하였다.

# Replication

## 레플리케이션이란?

같은 데이터를 여러 DB에 복사해 두는 것이다.

- 쓰기를 받는 DB를 **소스**(source, primary, master), 복사본을 **레플리카**(replica, slave)라고 부른다.
- 쓰기는 소스 한 곳에서만 받고, 읽기는 레플리카로 나눈다.

**왜 쓰는가?**

- 읽기 분산
  - 대부분의 서비스는 쓰기보다 읽기가 훨씬 많다.
  - 레플리카를 늘리면 읽기 처리량도 같이 늘어난다.
- 가용성
  - 소스가 죽으면 레플리카 하나를 소스로 승격시킨다. → 페일오버(failover)

**보충:** 레플리카는 쓰기를 분산하지 못한다. 레플리카가 10대여도 쓰기는 전부 소스 한 대가 받고, 그 변경이 10대에 똑같이 다시 적용된다. 쓰기가 병목이면 레플리카를 늘려도 소용없고, 그때부터 샤딩을 고민해야 한다.
{: .notice--info}

## MySQL 복제는 어떻게 일어나는가?

스레드 세 개가 나눠서 처리한다.

- 소스: 커밋된 변경을 **binlog**(바이너리 로그)에 기록
- 소스의 binlog dump 스레드: binlog를 레플리카로 전송
- 레플리카의 **I/O 스레드**: 받은 내용을 자기 쪽 **relay log**에 기록
- 레플리카의 **SQL 스레드**: relay log를 읽어서 실제 데이터에 적용

받는 스레드와 적용하는 스레드가 따로라서 적용이 느려도 수신은 계속된다. 대신 relay log에 쌓인 것과 실제 반영된 것 사이에 차이가 생기는데, 이게 **복제 지연(replication lag)** 이다.

## 비동기 / 반동기 / 동기

소스가 커밋을 확정하기 전에 레플리카를 얼마나 기다리는지에 따라 나뉜다.


| 방식  | 소스가 기다리는 것                      | 장점                    | 단점                         |
| --- | ------------------------------- | --------------------- | -------------------------- |
| 비동기 | 안 기다림                           | 쓰기가 제일 빠름             | 소스가 죽으면 아직 못 보낸 트랜잭션 유실 가능 |
| 반동기 | 레플리카 1대 이상이 relay log에 받았다는 ACK | 커밋된 데이터가 최소 한 곳에 더 있음 | 커밋마다 네트워크 왕복 추가            |
| 동기  | 레플리카가 적용까지 끝냄                   | 어디서 읽어도 같은 값          | 느리고, 레플리카 하나가 느리면 전체가 느려짐  |


- MySQL 기본값은 비동기, 반동기는 플러그인으로 켠다.
- 반동기(semi-sync)
  - MySQL 5.7부터 기본 모드는 `AFTER_SYNC`
    - binlog를 디스크에 쓴 뒤, 스토리지 엔진에 커밋하기 전에 ACK를 기다림
    - 클라이언트가 커밋 성공을 받았다면 그 트랜잭션은 이미 레플리카 relay log에도 있음
  - `rpl_semi_sync_source_timeout`(기본 10초) 안에 ACK가 안 오면 비동기로 내려간다.
    - 레플리카가 다 죽어도 쓰기가 멈추지는 않음
    - 대신 그동안은 비동기랑 똑같은 위험이 있음

**보충:** 반동기에서 레플리카가 확인해 주는 건 "받았다"까지다. 적용은 그 뒤에 따로 한다. 그래서 반동기로 바꿔도 복제 지연은 그대로 생긴다. 반동기가 막아주는 건 소스 장애 시 커밋된 데이터가 사라지는 문제다.
{: .notice--info}

## 복제 지연 때문에 생기는 문제

제일 흔한 건 **방금 쓴 데이터를 못 읽는 것**이다.

```
사용자가 프로필 수정       → 소스에 UPDATE
수정 후 프로필 화면 이동   → 레플리카에서 SELECT
레플리카에 아직 반영 안 됨 → 수정 전 프로필이 보임
```

이걸 보장하는 걸 read-after-write(read-your-writes) 일관성이라고 하는데, 비동기 복제에서는 기본으로 보장되지 않는다.

**대응 방법**

- 쓰기 직후의 읽기는 소스에서 한다.
  - 같은 트랜잭션 안에서 읽거나, 그 요청만 소스로 보냄
- 방금 쓴 사용자는 몇 초 동안 소스로 고정한다.
  - 세션이나 쿠키에 마지막 쓰기 시각을 남겨두고 판단
- 결제, 재고처럼 틀리면 안 되는 조회는 처음부터 소스에서 읽는다.
- 지연을 모니터링한다.
  - MySQL: `SHOW REPLICA STATUS`의 `Seconds_Behind_Source`
  - RDS: `ReplicaLag` 메트릭
  - 지연이 기준을 넘으면 그 레플리카를 읽기 대상에서 빼기도 함

인프런에 소스 1대 + 레플리카 2대로 읽기를 나눴더니 오히려 20~30% 느려졌다는 질문이 있었다. 질문자도 쓰기 직후 읽기를 소스로 보내야 하는지 고민하고 있었다. 레플리카를 붙인다고 그냥 빨라지는 건 아니고, 어떤 요청을 어디로 보낼지까지 같이 정해야 한다.

## Spring에서 읽기/쓰기 분리하기

`@Transactional(readOnly = true)`이면 레플리카로, 아니면 소스로 보내는 방식을 많이 쓴다. 라우팅은 `AbstractRoutingDataSource`로 한다.

```java
public class ReplicationRoutingDataSource extends AbstractRoutingDataSource {

    @Override
    protected Object determineCurrentLookupKey() {
        boolean readOnly = TransactionSynchronizationManager.isCurrentTransactionReadOnly();
        return readOnly ? "replica" : "source";
    }
}
```

```java
@Bean
public DataSource routingDataSource(DataSource sourceDataSource, DataSource replicaDataSource) {
    ReplicationRoutingDataSource routing = new ReplicationRoutingDataSource();
    routing.setTargetDataSources(Map.of(
            "source", sourceDataSource,
            "replica", replicaDataSource));
    routing.setDefaultTargetDataSource(sourceDataSource);
    return routing;
}

@Primary
@Bean
public DataSource dataSource(DataSource routingDataSource) {
    return new LazyConnectionDataSourceProxy(routingDataSource);
}
```

`**LazyConnectionDataSourceProxy`로 감싸지 않으면 모든 요청이 소스로 간다.**

- 트랜잭션 매니저는 트랜잭션을 시작할 때 커넥션부터 얻는다.
- `AbstractRoutingDataSource`는 커넥션을 얻는 순간 `determineCurrentLookupKey()`를 호출한다.
- 근데 그 시점에는 readOnly 플래그가 아직 세팅 전이다. → 항상 false → 항상 소스
- `LazyConnectionDataSourceProxy`는 일단 프록시 커넥션을 주고, 실제 쿼리가 나갈 때 진짜 커넥션을 얻는다.
  - 이때는 트랜잭션 설정이 끝난 상태라 readOnly 값이 제대로 보임

velog에 이 문제를 겪은 글이 있는데, 복제 지연 테스트가 실패해야 하는데 계속 통과해서 원인을 찾았다고 한다. 모든 쿼리가 소스로 가고 있었으니 지연이 보일 수가 없었던 것.

- 레플리카가 여러 대면 `determineCurrentLookupKey()`에서 라운드로빈으로 하나 고르면 된다.
- Aurora처럼 읽기 엔드포인트를 따로 주는 경우엔 그 엔드포인트 하나만 레플리카로 등록해도 된다.

# Sharding

## 샤딩이란?

데이터를 여러 DB에 **나눠서** 담는 것이다. 나눠진 DB 하나하나를 **샤드(shard)** 라고 부른다.

- 레플리케이션: 모든 DB가 같은 데이터
- 샤딩: 각 DB가 서로 다른 데이터

**왜 쓰는가?**

- 쓰기 분산, 저장 용량 분산
- 샤드 하나가 죽어도 그 샤드에 있는 데이터만 영향을 받음
- 대신 애플리케이션이 "이 데이터가 어느 샤드에 있는지" 알아야 함

## 수직 분할 vs 수평 분할

- **수직 분할**: 테이블 단위로 나눔
  - ex) 회원 테이블은 회원 DB, 주문 테이블은 주문 DB
  - MSA에서 서비스마다 DB를 따로 두는 것과 비슷
- **수평 분할**: 같은 테이블의 행(row)을 나눔
  - ex) 회원 ID 1~~100만은 샤드 0, 100만1~~200만은 샤드 1
  - 보통 샤딩이라고 하면 이쪽

**보충:** 파티셔닝이랑 헷갈리기 쉬운데, MySQL 파티셔닝은 DB 서버 한 대 안에서 테이블을 나눠 저장하는 기능이다. 샤딩은 서버 자체를 나눈다. 그래서 파티셔닝으로는 서버 한 대의 한계를 못 넘는다.
{: .notice--info}

## 샤딩 전략

어떤 데이터가 어느 샤드로 갈지는 **샤드 키**(회원 ID, 가게 ID 등)로 정한다. 샤드 키를 샤드 번호로 바꾸는 방법은 크게 네 가지다.

### Range

키의 범위로 나눈다.

- ex) ID 1~~1000 → 샤드 0, 1001~~2000 → 샤드 1
- 장점: 증설이 쉬움. 새 범위만 새 샤드에 배정하면 되고 기존 데이터는 안 옮겨도 됨
- 단점: 쏠림
  - ID가 계속 증가하면 새 데이터는 전부 마지막 샤드로 감
  - 최근 가입자가 제일 활발하면 트래픽도 마지막 샤드에 몰림

### Modular (Hash)

`샤드 키 % 샤드 수`로 정한다. 키를 해시한 다음 나머지를 쓰기도 한다.

- 장점: 데이터가 고르게 퍼짐
- 단점: 샤드 수가 바뀌면 대부분의 데이터 위치가 바뀜
  - ex) 3대 → 4대로 늘리면 `k % 3`이랑 `k % 4`가 같은 키는 4개 중 1개
  - → 75%를 옮겨야 함

### Directory (Lookup)

키와 샤드의 매핑을 별도 테이블에 적어둔다.

- 장점: 제일 유연함. 특정 대형 고객만 전용 샤드로 옮기는 것도 가능
- 단점: 매 요청마다 이 테이블을 봐야 함
  - 조회 비용이 들고, 이 테이블 자체가 단일 장애점(SPOF)이 됨
  - 그래서 보통 캐시를 같이 둠

### Consistent Hashing

해시 공간을 원(링)으로 놓고 샤드와 키를 둘 다 링 위에 올린다. 키는 시계 방향으로 가장 먼저 만나는 샤드에 저장된다.

- 장점: 샤드를 추가해도 새 샤드 바로 앞 구간만 옮기면 됨
  - 샤드 N대 → N+1대일 때 평균 1/(N+1) 정도만 이동
  - ex) 4대 → 5대면 약 20%. Modular의 75%랑 비교하면 차이가 큼
- 단점: 샤드 수가 적으면 구간 길이가 들쭉날쭉해서 고르게 안 퍼짐
  - → 샤드 하나를 **가상 노드** 여러 개로 링 위에 흩어 놓아서 해결
- DynamoDB, Cassandra 같은 분산 DB가 이 방식을 기반으로 한다.

## 샤드 키는 어떻게 골라야 하는가

샤딩에서 제일 중요하고, 나중에 바꾸기도 어려우므로 신중하게 골라야 함

- **카디널리티가 높아야 한다.**
  - 성별, 국가처럼 값 종류가 몇 개 없으면 샤드를 그 이상 못 늘림
- **값이 고르게 분포해야 한다.**
  - 특정 값에 데이터가 몰리면 그 샤드만 커짐
  - ex) 팔로워가 수천만 명인 셀럽 계정 → 핫 키(hot key) 문제
- **주요 쿼리가 샤드 하나에서 끝나야 한다.**
  - 회원 ID로 샤딩했는데 대부분 가게 ID로 조회한다면? → 조회할 때마다 모든 샤드를 뒤져야 함
- **단조 증가하는 키를 Range로 쓰면 쓰기가 한 샤드에 몰린다.**
  - 시간순 ID라면 해시를 섞는 게 나음

## 샤딩하면 생기는 문제

- **조인**
  - 다른 샤드에 있는 테이블끼리는 SQL 조인 불가
  - 애플리케이션에서 따로 조회해서 합치거나, 같이 조회되는 데이터는 같은 샤드 키로 묶어서 같은 샤드에 둠
- **집계, 정렬**
  - 전체 매출 합계, 전체 랭킹 → 모든 샤드에 쿼리 보내고 결과 합쳐야 함
  - 페이지네이션도 샤드마다 상위 N개 받아서 다시 정렬
  - 그래서 이런 조회는 분석용 DB로 따로 모으는 경우가 많음
- **트랜잭션**
  - 두 샤드에 걸친 쓰기는 한 트랜잭션으로 못 묶음
  - 2PC 같은 분산 트랜잭션은 느리고 복잡해서 잘 안 씀
  - 보통 트랜잭션이 샤드 하나에서 끝나도록 키를 설계하고, 어쩔 수 없으면 사가 패턴이나 아웃박스로 결과적 일관성을 맞춤
- **유일한 ID**
  - 샤드마다 `AUTO_INCREMENT`를 쓰면 ID가 겹침
  - 샤드마다 시작값/증가폭을 다르게 주거나, UUID, Snowflake 같은 ID 생성기 사용
  - Snowflake: 64비트에 타임스탬프 41비트 + 장비 번호 10비트 + 순번 12비트 → 시간순 정렬 가능, 서버끼리 안 겹침
- **리샤딩**
  - 샤드 수를 바꾸면 데이터를 옮겨야 하고, 옮기는 동안에도 서비스는 돌아가야 함
  - 옮기는 중에 들어온 쓰기를 어떻게 맞출지가 제일 까다로움

# 국내 사례

## 우아한형제들: 설정만으로 샤드 늘리기

우아한형제들 신사업부문 Thiiing(띠잉) 팀이 2020년에 쓴 글이다. 친구 관계를 저장하는 friend DB를 샤딩했다.

- 전략은 Range, Modular 두 가지를 정의함
  - Modular: 데이터 양이 일정하게 유지되는 곳
  - Range: 데이터가 빠르게 늘어나는 곳
  - ex) 콘텐츠는 초기에 24시간 보존 정책이라 양이 안 쌓여서 Modular가 맞았음
- friend DB는 Range, 샤드 키는 이미 있던 `userId`
  - 따로 ID 생성기를 만들 필요가 없었음
- Range 규칙의 마지막 샤드 `range_max`를 키의 최댓값으로 잡아둠
  - 증설을 미리 못 해도 새 데이터가 갈 곳이 없어지는 일은 없음
- 증설 절차: 물리 DB 추가 → yaml에 데이터소스, 샤딩 규칙 추가 → 배포
- 구현
  - `@Sharding` 어노테이션 + AOP
  - 메서드 첫 번째 파라미터를 샤드 키로 쓰는 팀 규칙을 정하고, Aspect가 그 값을 ThreadLocal에 넣음
  - 라우터는 `AbstractRoutingDataSource`를 상속해서 ThreadLocal의 샤드 키로 샤드를 고르고, readOnly면 그 샤드의 레플리카, 아니면 소스를 고름
  - 여기서도 `LazyConnectionDataSourceProxy`로 감쌈

**보충:** 샤드마다 소스 1대 + 레플리카 여러 대를 둔 구조다. 실무에서는 이렇게 둘을 같이 쓰는 경우가 많다. 샤딩이 쓰기와 용량을, 레플리케이션이 읽기와 가용성을 맡는다. 그리고 ThreadLocal은 스레드 풀에서 스레드가 재사용되기 때문에 요청이 끝나면 꼭 비워야 한다. 예외가 나도 비워지도록 `finally`에서 정리하는 게 안전하다.
{: .notice--info}

## G마켓: 수억 건 상품 DB를 MySQL 클러스터로

G마켓 Item Engineering 팀이 2022년에 쓴 글이다. 상품 DB 한 곳에 읽기, 쓰기가 다 몰려 있었고 이 DB가 죽으면 전사 장애로 번질 수 있었다.

- CQRS로 쓰기 DB와 읽기 DB를 나누면서 읽기 쪽을 Sharded MySQL로 구성
  - 기존 쓰기 DB는 MSSQL
- 샤딩은 수평 분할 + Modular
  - 자원을 고르게 쓰는 걸 우선함
  - 증설할 때는 샤드 수를 **배수**로 늘리기로 함
- 라우팅은 ShardingSphere-JDBC
  - 여러 샤드에 나뉜 테이블을 하나처럼 쓸 수 있게 해줌
- MSSQL 변경분은 Spark Streaming → Kafka → Spring Kafka 컨슈머 → MySQL로 반영
  - Debezium 구조를 참고해서 직접 구현
- 마이그레이션은 처음엔 단순 insert로 하려다 **Upsert**로 변경
  - 소스/레플리카 사이 복제 지연 때문에 시간이 안 줄었음
  - Upsert면 실시간 반영 컨슈머랑 마이그레이션을 동시에 돌려도 정합성이 맞음
- 운영 배포 후 Pod마다 첫 요청이 약 3초 걸리는 문제
  - ShardingSphere가 SQL을 처음 받을 때 파싱하고 캐시하는 비용이었음
  - 앱이 뜬 직후 샤드 키 0~3으로 한 번씩 호출하는 워밍업 코드로 해결
  - 개발 서버는 Pod가 1개라 못 봤던 문제

**왜 배수로 늘리나?**

- 2대 → 4대로 늘리면 `k % 2 == 0`인 키는 `k % 4`가 0 아니면 2
  - 샤드 0의 데이터는 샤드 0에 남거나 샤드 2로만 감
  - 옮기는 양은 절반이지만, 기존 샤드 하나가 새 샤드 하나로 그대로 쪼개지는 모양이라 작업이 단순함
- 3대 → 4대는 75%가 여기저기 섞여서 움직임

## 샤딩, 꼭 해야 하나?

ITWorld에 실린 번역 칼럼 제목이 "샤딩, 웬만하면 하지 마라"다.

- 한 샤드에 부하가 몰리면 고객 데이터를 옮겨야 하는데 이게 복잡하고 위험함
- 그 전에 서비스/기능 단위로 데이터를 나누는 방법부터 보라고 함

G마켓 글도 마지막에 개발자가 신경 쓸 게 많아져서 생산성이 떨어졌다고 적었다. 샤딩은 한 번 하면 되돌리기 어려우니까 그 전에 이것들부터 보는 게 맞다.

- 느린 쿼리, 인덱스
- 스케일 업
- 캐시 (자주 읽는 데이터는 Redis로)
- 레플리카 (읽기가 문제라면 이걸로 충분한 경우가 많음)
- 수직 분할 (도메인별로 DB 분리)
- 오래된 데이터 아카이빙

이걸 다 했는데도 쓰기를 한 대로 못 받거나, 테이블 하나가 서버 한 대에 안 들어갈 때 샤딩을 꺼내면 된다.

# 정리


|              | 레플리케이션             | 샤딩                       |
| ------------ | ------------------ | ------------------------ |
| 각 DB가 가진 데이터 | 전부 같음              | 서로 다름                    |
| 분산되는 것       | 읽기                 | 쓰기, 용량, 읽기               |
| 가용성          | 페일오버로 높아짐          | 장애 범위가 샤드 하나로 줄어듦        |
| 주된 문제        | 복제 지연, 방금 쓴 걸 못 읽음 | 조인, 집계, 분산 트랜잭션, ID, 리샤딩 |
| 애플리케이션 변경    | readOnly 기준 라우팅    | 샤드 키 기준 라우팅, 쿼리 설계 변경    |


- 레플리케이션은 쓰기를 못 나눈다. 쓰기가 병목이면 샤딩이나 수직 분할을 봐야 한다.
- 비동기 복제에서는 쓰기 직후 읽기를 소스로 보내야 할 때가 있다. 반동기로 바꿔도 적용 지연은 남는다.
- Spring에서 readOnly로 라우팅할 땐 `LazyConnectionDataSourceProxy`를 꼭 같이 쓴다.
- 증설이 잦으면 Range나 Consistent Hashing, 고른 분포가 중요하면 Modular. Modular라면 배수로 늘리는 게 덜 아프다.
- 샤드 키는 주요 쿼리가 샤드 하나에서 끝나도록 고른다.
