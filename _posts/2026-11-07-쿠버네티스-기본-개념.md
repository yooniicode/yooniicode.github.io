# 1. 쿠버네티스는 무엇을 해주는 도구일까

> **`쿠버네티스(Kubernetes, K8s)`**는 여러 서버에 걸쳐 컨테이너를 배포하고, 개수를 유지하고, 연결해 주는 컨테이너 오케스트레이션 도구임

  <img src="{{ '/assets/images/posts/2026-11-07-kubernetes-basics/container-evolution.svg' | relative_url }}"
       alt="전통적 배포, 가상화 배포, 컨테이너 배포 구조를 비교한 그림" loading="lazy" decoding="async">
  <figcaption>전통적 배포 → 가상 머신 → 컨테이너로 바뀌어 온 배포 방식 (출처: <a href="https://kubernetes.io/ko/docs/concepts/overview/">쿠버네티스 공식 문서</a>, CC BY 4.0)</figcaption>
</figure>

## Docker만 쓰면 뭐가 불편할까

- 서버 한 대에 컨테이너 몇 개면 `docker run`으로 충분함
- 서버가 여러 대, 컨테이너가 수십 개가 되면 사람이 챙길 게 많아짐
  - 컨테이너가 죽으면 누가 다시 띄움?
  - 새 컨테이너를 어느 서버에 올림? 남은 CPU, 메모리는 누가 계산함?
  - 컨테이너 IP가 바뀌면 다른 서비스는 어디로 요청을 보냄?
  - 새 버전 배포할 때 서비스를 끊지 않고 하나씩 교체하려면?
- 쿠버네티스는 이걸 클러스터가 대신 처리해 줌

## 명령형과 선언형

- Docker는 "이 컨테이너 띄워"라고 **행동을 명령**하는 방식임
- 쿠버네티스는 "이 컨테이너가 항상 3개 떠 있어야 함"이라고 **원하는 상태를 선언**하는 방식임
  - 컨트롤러가 현재 상태를 계속 지켜보다가 원하는 상태와 다르면 맞춰 줌
  - 이 반복을 reconciliation loop(조정 루프)라고 부름
  - ex) Pod 하나가 죽어서 2개가 됨 → 컨트롤러가 차이를 발견 → 하나 새로 만듦

비유로 보면 에어컨 희망 온도와 비슷합니다.

| 구분 | 에어컨 | 쿠버네티스 |
| --- | --- | --- |
| 원하는 상태 | 희망 온도 24도 | `replicas: 3` |
| 현재 상태 | 실내 온도 27도 | 실행 중인 Pod 2개 |
| 맞추는 주체 | 온도 센서와 컴프레서 | 컨트롤러 |
| 사람이 하는 일 | 온도만 정함 | YAML만 정함 |

> 💡 그래서 쿠버네티스에서는 `kubectl run`처럼 명령으로 만드는 것보다 YAML 파일을 `kubectl apply`로 적용하는 방식을 주로 씀. 파일이 곧 원하는 상태라서 Git으로 관리하기도 좋음

# 2. 클러스터는 어떻게 생겼을까

> **`클러스터`**는 쿠버네티스가 관리하는 서버 묶음임. 크게 두뇌 역할의 **컨트롤 플레인**과 실제 컨테이너가 돌아가는 **워커 노드**로 나뉨

<figure>
  <img src="{{ '/assets/images/posts/2026-11-07-kubernetes-basics/components-of-kubernetes.svg' | relative_url }}"
       alt="컨트롤 플레인의 api, etcd, sched, c-m과 노드의 kubelet, k-proxy가 API 서버로 연결된 클러스터 구성도" loading="lazy" decoding="async">
  <figcaption>클러스터 구성. 모든 연결이 가운데 API 서버를 거침 (출처: <a href="https://kubernetes.io/ko/docs/concepts/overview/components/">쿠버네티스 공식 문서</a>, CC BY 4.0)</figcaption>
</figure>

## 컨트롤 플레인

- `kube-apiserver`
  - 클러스터의 유일한 출입구임
  - `kubectl`도, 다른 컴포넌트도 전부 API 서버를 거쳐서 통신함
- `etcd`
  - 클러스터의 모든 상태를 저장하는 키-값 저장소임
  - 원하는 상태와 현재 상태가 전부 여기 기록됨 → etcd가 날아가면 클러스터 정보도 날아감
- `kube-scheduler`
  - 아직 노드가 정해지지 않은 Pod를 보고 어느 노드에 올릴지 정함
  - 노드의 남은 자원, Pod가 요청한 자원 등을 따짐
- `kube-controller-manager`
  - Deployment, ReplicaSet, Node 같은 컨트롤러들을 실행함
  - 위에서 말한 조정 루프가 여기서 돌아감

## 워커 노드

- `kubelet`
  - 노드마다 하나씩 있는 에이전트임
  - 자기 노드에 배정된 Pod를 보고 컨테이너 런타임에 실행을 맡김
  - 컨테이너 상태를 API 서버에 보고함
- `kube-proxy`
  - Service로 들어온 트래픽이 실제 Pod로 가도록 노드의 네트워크 규칙을 관리함
- 컨테이너 런타임
  - 실제로 컨테이너를 실행하는 프로그램임. 요즘은 주로 `containerd`를 씀

| 컴포넌트 | 위치 | 한 줄 역할 |
| --- | --- | --- |
| kube-apiserver | 컨트롤 플레인 | 모든 요청의 출입구 |
| etcd | 컨트롤 플레인 | 클러스터 상태 저장소 |
| kube-scheduler | 컨트롤 플레인 | Pod를 올릴 노드 결정 |
| kube-controller-manager | 컨트롤 플레인 | 원하는 상태로 맞추는 루프 |
| kubelet | 워커 노드 | 배정된 Pod 실행, 상태 보고 |
| kube-proxy | 워커 노드 | Service 트래픽 전달 |

# 3. Pod는 컨테이너와 뭐가 다를까

> **`Pod`**는 쿠버네티스에서 만들고 관리하는 가장 작은 배포 단위임. 컨테이너를 하나 이상 감싸는 껍데기라고 보면 됨

- 쿠버네티스는 컨테이너를 직접 다루지 않고 Pod 단위로 다룸
- 한 Pod 안의 컨테이너들은 같은 네트워크와 볼륨을 공유함
  - IP가 하나라서 서로 `localhost`로 통신 가능
  - ex) 앱 컨테이너 + 로그를 수집하는 사이드카 컨테이너
- 대부분은 Pod 하나에 컨테이너 하나를 넣음
- Pod는 일회용임
  - 죽으면 같은 Pod가 살아나는 게 아니고 새 Pod가 만들어짐
  - 새 Pod는 IP도 바뀜 → 이 문제를 Service가 해결함 (5장)

<figure>
  <img src="{{ '/assets/images/posts/2026-11-07-kubernetes-basics/pod-in-node.svg' | relative_url }}"
       alt="노드 안에 IP가 각각 다른 Pod 4개가 있고 Pod 안에 컨테이너와 볼륨이 들어 있는 그림" loading="lazy" decoding="async">
  <figcaption>노드 하나에 Pod 여러 개. Pod마다 IP가 하나씩 있고 안에 컨테이너와 볼륨이 들어감. 그림 속 Docker 자리는 요즘 보통 containerd임 (출처: <a href="https://kubernetes.io/docs/tutorials/kubernetes-basics/explore/explore-intro/">쿠버네티스 공식 문서</a>, CC BY 4.0)</figcaption>
</figure>

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: api
  labels:
    app: api          # Service가 이 라벨로 Pod를 찾음
spec:
  containers:
    - name: api
      image: myrepo/api:1.0.0
      ports:
        - containerPort: 8080
```

> Pod를 이렇게 직접 만드는 경우는 거의 없음. Pod만 만들면 죽었을 때 다시 만들어 줄 주체가 없기 때문임. 보통은 다음 장의 Deployment로 만듦

# 4. Deployment는 Pod를 어떻게 유지할까

> **`Deployment`**는 "이 Pod를 몇 개 유지하고, 버전은 어떻게 바꿀지"를 선언하는 오브젝트임

## Deployment, ReplicaSet, Pod의 관계

- Deployment → ReplicaSet → Pod 순서로 만들어짐
  - ReplicaSet은 Pod 개수를 `replicas`만큼 유지하는 역할임
  - Deployment는 ReplicaSet을 관리하면서 버전 교체를 담당함
- 사람은 Deployment만 만들고 ReplicaSet은 거의 직접 건드리지 않음

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api
  template:            # 이 아래가 만들어질 Pod의 모양
    metadata:
      labels:
        app: api
    spec:
      containers:
        - name: api
          image: myrepo/api:1.0.0
          ports:
            - containerPort: 8080
```

## 롤링 업데이트

- 이미지 태그를 `1.0.0` → `1.1.0`으로 바꾸고 다시 apply하면 롤링 업데이트가 일어남
  - 새 ReplicaSet을 만들고 새 Pod를 조금씩 늘림
  - 동시에 옛 ReplicaSet의 Pod를 조금씩 줄임
  - 서비스가 끊기지 않고 교체됨

<figure>
  <img src="{{ '/assets/images/posts/2026-11-07-kubernetes-basics/rolling-update.svg' | relative_url }}"
       alt="롤링 업데이트 중 Pod 하나가 새 버전으로 바뀌며 새 IP를 받고 Service가 계속 묶고 있는 그림" loading="lazy" decoding="async">
  <figcaption>롤링 업데이트 도중. 새 버전 Pod는 새 IP를 받고, Service는 바뀐 Pod까지 계속 묶어서 트래픽을 보냄 (출처: <a href="https://kubernetes.io/docs/tutorials/kubernetes-basics/update/update-intro/">쿠버네티스 공식 문서</a>, CC BY 4.0)</figcaption>
</figure>
- 속도는 두 값으로 조절함
  - `maxSurge`: 원래 개수보다 최대 몇 개까지 더 띄울 수 있는지 (기본 25%)
  - `maxUnavailable`: 교체 중 최대 몇 개까지 빠져 있어도 되는지 (기본 25%)
- 옛 ReplicaSet은 Pod 0개 상태로 남아 있음
  - 그래서 `kubectl rollout undo`로 이전 버전으로 바로 돌아갈 수 있음

```bash
kubectl apply -f deployment.yaml          # 원하는 상태 적용
kubectl get deploy,rs,pod                 # Deployment, ReplicaSet, Pod 한 번에 보기
kubectl rollout status deploy/api         # 롤링 업데이트 진행 상황 보기
kubectl rollout undo deploy/api           # 직전 버전으로 되돌리기
```

# 5. Pod IP는 계속 바뀌는데 어떻게 접속할까

> **`Service`**는 라벨로 묶인 Pod들 앞에 고정된 주소를 하나 붙여 주는 오브젝트임

- Pod는 죽고 새로 뜰 때마다 IP가 바뀜 → IP로 직접 호출하면 언젠가 깨짐
- Service는 고정 IP와 DNS 이름을 가짐
  - `selector`에 적은 라벨을 가진 Pod들을 찾아서 트래픽을 나눠 보냄
  - 연결 대상 목록은 EndpointSlice라는 오브젝트로 자동 관리됨
  - 클러스터 안에서는 `api.default.svc.cluster.local` 같은 이름으로 호출 가능. 같은 네임스페이스면 `api`만 써도 됨

<figure>
  <img src="{{ '/assets/images/posts/2026-11-07-kubernetes-basics/service-selector.svg' | relative_url }}"
       alt="Service가 selector app=A로 라벨이 app: A인 Pod들에만 트래픽을 보내고 app: B Pod는 제외하는 그림" loading="lazy" decoding="async">
  <figcaption>Service는 selector(app=A)와 라벨이 맞는 Pod에만 트래픽을 보냄. app: B인 Pod는 대상이 아님 (출처: <a href="https://kubernetes.io/docs/tutorials/kubernetes-basics/expose/expose-intro/">쿠버네티스 공식 문서</a>, CC BY 4.0)</figcaption>
</figure>

```yaml
apiVersion: v1
kind: Service
metadata:
  name: api
spec:
  type: ClusterIP
  selector:
    app: api           # 이 라벨을 가진 Pod로 트래픽 전달
  ports:
    - port: 80         # Service가 받는 포트
      targetPort: 8080 # Pod 컨테이너 포트
```

## Service 타입

- `ClusterIP`
  - 기본값임. 클러스터 안에서만 접근 가능
  - 내부 API 서버, DB처럼 밖에 노출할 필요 없는 것에 씀
- `NodePort`
  - 모든 노드의 특정 포트(30000~32767)를 열어서 외부에서 접근 가능하게 함
  - 테스트용으로는 편하지만 운영에서는 잘 안 씀
- `LoadBalancer`
  - 클라우드의 로드밸런서(AWS면 ELB)를 만들어서 앞에 붙임
  - 서비스마다 로드밸런서가 하나씩 생겨서 비용이 늘어남

## Ingress

- 외부 HTTP 요청을 경로나 도메인 기준으로 여러 Service에 나눠 주는 규칙임
  - ex) `/api` → api Service, `/` → web Service
- 로드밸런서 하나로 여러 Service를 묶을 수 있음
- Ingress 오브젝트만 만들면 아무 일도 안 일어남 → 실제로 규칙을 처리하는 Ingress Controller를 따로 설치해야 함

> Ingress 다음 세대로 Gateway API도 나와 있음. 역할을 인프라 담당과 앱 담당으로 나눠서 설정할 수 있는 게 특징임. 새로 시작한다면 같이 살펴볼 만함

# 6. 설정값과 비밀값은 어디에 둘까

- `ConfigMap`
  - DB 주소, 프로파일 이름 같은 일반 설정값을 담음
  - 환경 변수나 파일로 Pod에 넣어 줌
  - 이미지와 설정을 분리할 수 있음 → 같은 이미지를 dev, prod에 그대로 씀
- `Secret`
  - 비밀번호, API 키 같은 민감한 값을 담음
  - 다만 기본으로는 base64 인코딩만 되어 있음. 인코딩은 누구나 디코딩 가능하니 암호화는 아님
  - 실제로 보호하려면 etcd 저장 시 암호화 설정, 접근 권한(RBAC) 제한을 같이 해야 함

> 처음에 Secret이면 알아서 암호화되는 줄 알았는데 아니었음. `kubectl get secret -o yaml`로 보이는 값을 base64 디코딩하면 원문이 그대로 나옴

# 7. 컨테이너가 정상인지는 어떻게 알까

> **`Probe`**는 kubelet이 컨테이너 상태를 주기적으로 확인하는 검사임

- 프로세스가 떠 있다고 앱이 정상인 건 아님
  - ex) Spring 앱이 데드락에 걸려 응답을 못 해도 JVM 프로세스는 살아 있음
- 그래서 세 종류의 검사를 따로 둠
  - `livenessProbe`
    - 살아 있는지 확인함
    - 실패하면 컨테이너를 재시작함
  - `readinessProbe`
    - 요청을 받을 준비가 됐는지 확인함
    - 실패하면 재시작은 안 하고 Service 대상에서만 뺌
  - `startupProbe`
    - 시작이 끝났는지 확인함
    - 성공하기 전까지 나머지 두 검사를 미룸 → 기동이 느린 앱이 시작 도중 재시작되는 걸 막음

Spring Boot는 쿠버네티스 위에서 실행되면 Actuator가 이 검사용 엔드포인트를 자동으로 열어 줍니다.

```yaml
livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
```

> liveness 검사에 DB 연결 확인까지 넣으면 위험함. DB가 잠깐 느려졌을 뿐인데 모든 Pod가 동시에 재시작될 수 있음. 외부 의존성은 readiness 쪽에서 보는 게 일반적임

# 8. kubectl apply 한 줄이 실제로 하는 일

앞에서 본 컴포넌트와 오브젝트를 Deployment 하나 적용하는 흐름으로 이어 보면 이렇습니다.

1. `kubectl apply -f deployment.yaml`
   - kubectl이 YAML을 `kube-apiserver`로 보냄
2. API 서버가 요청을 검증하고 `etcd`에 Deployment를 저장함
   - 이 시점에는 Deployment라는 기록만 생긴 상태임
3. Deployment 컨트롤러가 새 Deployment를 발견하고 ReplicaSet을 만듦
4. ReplicaSet 컨트롤러가 Pod가 0개인 걸 보고 Pod 3개를 만듦
   - 아직 어느 노드에서 돌지 정해지지 않은 상태임
5. `kube-scheduler`가 노드가 비어 있는 Pod를 보고 노드를 배정함
6. 해당 노드의 `kubelet`이 자기에게 배정된 Pod를 보고 `containerd`에 컨테이너 실행을 맡김
7. readinessProbe를 통과하면 Pod가 Service의 EndpointSlice에 등록됨
   - 이때부터 실제 트래픽을 받음

- 컴포넌트끼리 서로 직접 명령하지 않음
  - 전부 API 서버에 상태를 쓰고, 각자 API 서버를 지켜보다가 자기 일을 함
  - 그래서 중간에 하나가 잠깐 죽어도 다시 살아나면 밀린 상태를 보고 이어서 처리함

### 정리

| 오브젝트 | 하는 일 | 없으면 생기는 문제 |
| --- | --- | --- |
| Pod | 컨테이너를 감싸는 최소 배포 단위 | 쿠버네티스가 컨테이너를 다룰 수 없음 |
| ReplicaSet | Pod 개수 유지 | 죽은 Pod가 다시 안 생김 |
| Deployment | ReplicaSet 관리, 롤링 업데이트, 롤백 | 버전 교체 때 서비스가 끊김 |
| Service | 바뀌는 Pod 앞에 고정 주소 제공 | Pod IP가 바뀔 때마다 호출이 깨짐 |
| Ingress | 외부 HTTP 요청을 경로, 도메인별로 분배 | Service마다 로드밸런서가 필요함 |
| ConfigMap, Secret | 설정과 비밀값을 이미지 밖으로 분리 | 환경마다 이미지를 새로 빌드해야 함 |
| Probe | 컨테이너 상태 검사 | 멈춘 앱에도 트래픽이 계속 감 |


# 9. Docker만 쓸 때와 비교하면 뭐가 좋을까

정리하고 나니 결국 Docker로도 되는 거 아닌가 하는 생각이 들었습니다. 그래서 Docker(와 Docker Compose)만 쓸 때와 쿠버네티스를 비교해보았습니다..

## 둘은 같은 층의 도구가 아님

- Docker는 컨테이너를 **만들고 실행하는** 도구임
  - 이미지 빌드, 컨테이너 실행이 주 역할임
  - Docker Compose를 써도 기본적으로 서버 한 대 안에서 여러 컨테이너를 묶는 수준임
- 쿠버네티스는 이미 만들어진 컨테이너를 **여러 서버에 걸쳐 운영하는** 도구임
  - 이미지는 여전히 Docker 등으로 빌드함
  - 그래서 둘 중 하나를 고르는 관계라기보다 Docker 위에 운영 계층을 하나 더 얹는 관계에 가까움

## 이점 1. 서버가 죽어도 다른 서버로 옮겨 띄움

- Docker도 `restart: always`로 컨테이너가 죽으면 다시 띄울 수 있음
  - 다만 그 서버 안에서만 가능함 → 서버 자체가 죽으면 컨테이너도 같이 사라짐
- 쿠버네티스는 노드가 죽으면 그 노드에 있던 Pod를 다른 노드에 새로 만듦
  - 원하는 상태가 `replicas: 3`이니 컨트롤러가 다시 3개로 맞춤

## 이점 2. 헬스체크 결과로 실제 조치를 함

- Docker에도 `HEALTHCHECK`가 있음
  - 하지만 Docker 단독으로는 unhealthy가 떠도 상태 표시만 바뀌고 재시작이나 트래픽 차단은 안 함
- 쿠버네티스는 Probe 결과에 따라 바로 행동함
  - liveness 실패 → 재시작
  - readiness 실패 → Service 대상에서 빼서 트래픽을 막음

## 이점 3. 무중단 배포와 롤백이 기본 기능임

- Docker Compose로 이미지를 바꾸면 보통 컨테이너를 내리고 새로 띄움 → 그 사이 잠깐 끊김
  - 무중단으로 하려면 Nginx 앞단 설정, 블루그린 스크립트 등을 직접 만들어야 함
- 쿠버네티스는 Deployment의 롤링 업데이트가 기본임
  - `maxSurge`, `maxUnavailable`로 속도 조절 가능
  - readiness를 통과한 새 Pod에만 트래픽이 감
  - `kubectl rollout undo` 한 줄로 이전 버전 복귀

## 이점 4. 여러 서버에 걸친 스케일링과 자동 배치

- Docker는 컨테이너를 어느 서버에 띄울지 사람이 정함
- 쿠버네티스는 scheduler가 노드별 남은 자원을 보고 알아서 배치함
  - `kubectl scale deploy/api --replicas=10` 한 줄로 늘리면 여러 노드에 나눠 올라감
  - HPA(Horizontal Pod Autoscaler)를 쓰면 CPU 사용량 등을 보고 Pod 개수도 자동으로 조절함

## 이점 5. 서비스 디스커버리와 로드밸런싱

- Docker Compose도 같은 네트워크 안에서는 서비스 이름으로 호출 가능함
  - 다만 서버 한 대 범위임
- 쿠버네티스는 Service가 여러 노드에 흩어진 Pod 앞에 고정 주소를 붙이고 트래픽을 나눠 줌
  - Pod가 몇 개로 늘든, 어느 노드로 옮겨 가든 호출하는 쪽은 Service 이름만 알면 됨

## 그럼 무조건 쿠버네티스가 좋을까

- 그렇지는 않음
  - 컨트롤 플레인, 노드, 네트워크 플러그인 등 관리할 게 늘어남
  - EKS 같은 관리형 서비스를 써도 컨트롤 플레인 비용이 따로 나감
  - YAML, RBAC, 네트워크 개념 등 배워야 할 게 많음
- 서버 한두 대에 서비스 몇 개라면 Docker Compose나 Railway 같은 PaaS가 더 단순함
- 서버가 여러 대이고, 무중단 배포와 자동 복구가 꼭 필요하고, 트래픽 변화가 클 때 쿠버네티스의 이점이 커짐

| 기능 | Docker, Docker Compose | 쿠버네티스 |
| --- | --- | --- |
| 실행 범위 | 주로 서버 한 대 | 여러 노드로 된 클러스터 |
| 컨테이너가 죽었을 때 | 같은 서버에서 재시작 | 재시작, 필요하면 다른 노드에 새로 생성 |
| 서버가 죽었을 때 | 컨테이너도 같이 중단 | 다른 노드에 다시 배치 |
| 헬스체크 | 상태 표시 위주 | 재시작, 트래픽 차단까지 자동 |
| 배포 | 내리고 다시 띄움, 무중단은 직접 구성 | 롤링 업데이트, 롤백 기본 제공 |
| 스케일링 | 수동, 배치도 수동 | 명령 한 줄 또는 HPA 자동, 배치는 scheduler |
| 서비스 연결 | 같은 호스트 네트워크 안에서 이름 호출 | Service로 클러스터 전체에서 고정 주소 |
| 운영 부담 | 낮음 | 높음 |

정리해 보니 쿠버네티스의 이점은 대부분 **서버가 여러 대일 때** 체감할 수 있고 그 이상은 오버엔지니어링으로 판단할 수 있을 것 같습니다... 서버 한 대 안에서는 Docker로도 충분히 할 수 있는 일이 많기 때문입니다..
