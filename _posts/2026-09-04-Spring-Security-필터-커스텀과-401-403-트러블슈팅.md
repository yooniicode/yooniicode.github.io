프로젝트에 JWT 인증을 붙이면서 Spring Security를 제대로 마주했다.
토큰 검증 필터 하나 만들고 `@PreAuthorize` 붙이면 끝이겠지라고 생각했었는데,
로그인 안 한 유저가 401이 아니라 403을 받는 상황에서 해당 방식의 모순점이 생겼었다.

1. **커스텀 필터 만들기** — `JwtAuthenticationFilter`, `UserDetails` 구현까지
2. **401/403 트러블슈팅** — 왜 익명 유저가 403을 받았고, 왜 내가 등록한 `AccessDeniedHandler`는 호출되지 않았는가

---

# 0. 용어 정리

## JWT Token
서버가 서명한 데이터(= claims)가 들어있는 토큰.

구조는 `header.payload.signature` 세 부분이 `.` 으로 이어진 형태이고, 각각 **Base64URL**로 인코딩되어 있다.

```
eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiIxIiwicm9sZSI6IlVTRVIifQ . dBjftJeZ4CVP...
   header(알고리즘)         payload(claims)                    signature(서명)
```

> ⚠️ 인코딩 ≠ 암호화. payload는 누구나 디코딩해서 볼 수 있다.
> **비밀번호 같은 민감 정보를 claim에 넣으면 안 된다.**
> JWT가 보장하는 건 기밀성이 아니라 **무결성**(서버 서명으로 위조 여부를 검증)이다.

## Claim
토큰 안에 들어가는 데이터 필드들.

| claim | 의미 |
| --- | --- |
| `sub` | subject, 보통 userId |
| `exp` | 만료 시간 (expiration) |
| `iat` | 발급 시간 (issued at) |
| `roles` | `ROLE_USER`, `ROLE_ADMIN` 등 권한 |

## Authentication (Spring Security)
현재 요청에서 로그인한 사용자의 **신분 및 권한 정보를 담은 객체**.
두 가지 용도로 쓰인다.

1. 사용자가 제공한 자격 증명(ID/PW 등)을 담아 `AuthenticationManager`에 전달하는 용도 (`isAuthenticated() == false`)
2. 인증에 성공한 현재 사용자를 나타내는 용도

구성 요소는 다음과 같다.

- **Principal**: 사용자 식별 (주로 `UserDetails` 인스턴스)
- **Credentials**: 자격 증명 (비밀번호 등, 인증 후 보안을 위해 주로 삭제됨)
- **Authorities**: 부여된 권한 목록 (`GrantedAuthority`)
- **Details**: 인증 부가 정보 (IP, 세션 ID 등)
- **Authenticated**: 인증 여부 (boolean)

## SecurityContext
`SecurityContextHolder` 안에 저장되는 객체로, 현재 인증된 사용자의 `Authentication` 객체를 포함한다.

## SecurityContextHolder
Spring Security 인증 모델의 **핵심 저장소**로, '누가' 인증되었는지에 대한 상세 정보를 보관한다.
`ThreadLocal`을 사용하여 같은 스레드 내에서는 어디서든 접근 가능하도록 한다.

```java
Authentication auth = SecurityContextHolder.getContext().getAuthentication();
```

> 💡 `ThreadLocal` 기반이라는 게 중요한 함정이다.
> `@Async`나 별도 스레드 풀로 작업을 넘기면 SecurityContext가 따라가지 않는다.
> 필요하면 `SecurityContextHolder.setStrategyName(MODE_INHERITABLETHREADLOCAL)`을 쓰거나,
> `DelegatingSecurityContextExecutor`로 감싸야 한다.

# 1. 스프링 동작 방식 — Filter는 스프링 '바깥'에 있다

{% include post-image.html src="spring-request-flow.png" width="1878" height="742"
   alt="Client에서 시작해 Filter(Web Context)를 지나 DispatcherServlet, Interceptor, Controller(Spring Context)로 들어가는 요청 흐름" %}

**Filter는 Web Context(서블릿 컨테이너)에, Interceptor와 Controller는 Spring Context에 있다.**
즉 Security Filter는 스프링 MVC보다 **앞**에 있고, 스프링의 `@ControllerAdvice` 같은 건 아직 관여할 수 없는 영역이다.

전체 흐름으로는,

```
Client
  ↓
[Servlet Container (Tomcat 등)]
  ↓
(Filter Chain)  ← 서블릿 표준 (스프링 바깥/앞)
  ↓
DispatcherServlet  ← Spring MVC의 Front Controller
  ↓
HandlerMapping / HandlerAdapter
  ↓
(Interceptor.preHandle)  ← 스프링 MVC 내부
  ↓
Controller (@RequestMapping 등)
  ↓
(Interceptor.postHandle)
  ↓
ViewResolver / HttpMessageConverter (JSON 등 응답 생성)
  ↓
(Interceptor.afterCompletion)
  ↓
(Filter 후처리)
  ↓
Response
```

## 에러 처리 흐름

```
WAS(톰캣) → 필터 → 서블릿(디스패처 서블릿) → 인터셉터 → 컨트롤러
  → 컨트롤러(예외 발생) → 인터셉터 → 서블릿(디스패처 서블릿) → 필터 → WAS(톰캣)
  → WAS(톰캣) → 필터 → 서블릿(디스패처 서블릿) → 인터셉터 → 컨트롤러(BasicErrorController)
```

컨트롤러에서 터진 예외가 처리되지 않으면 WAS까지 올라갔다가, WAS가 `/error`로 **다시 요청을 보내면서** 필터를 한 번 더 타고 `BasicErrorController`에 도달한다.
이 "다시 요청"이 뒤에서 이야기할 필터 중복 실행 문제와도 연결된다.

# 2. 커스텀 필터 만들기

## 2-1. CustomFilter가 하는 일

> 클라이언트에서 API 요청 시, `HttpServletRequest`의 Header에서 토큰을 꺼내 유효성을 검증하고
> 정보를 읽어 `Authentication` 객체를 만들고 `SecurityContext`에 저장하는 필터

한 줄 요약: **"헤더 → 토큰 → 검증 → Authentication → SecurityContext"**.

## 2-2. `OncePerRequestFilter` vs `GenericFilterBean`

`doFilter(Internal)` 메서드는 토큰의 인증정보를 `SecurityContext`에 저장하는 역할을 수행한다.
그런데 어떤 부모 클래스를 상속하느냐에 따라 **몇 번 실행되는지**가 달라진다.

Spring MVC에서 request의 lifecycle을 나타내는 그림을 먼저 보자.

{% include post-image.html src="spring-mvc-lifecycle.png" width="784" height="693"
   alt="Spring MVC request life cycle: Filter → DispatcherServlet → HandlerMapping/HandlerInterceptor → Handler → HandlerExceptionResolver → ViewResolver → Response" %}

### GenericFilterBean

- `Filter`를 확장하여 스프링에서 제공하는 필터, `doFilter` 메서드를 구현한다.
- 기존 필터에서 얻어올 수 없는 정보였던 **스프링의 설정 정보를 가져올 수 있게 확장된 추상 클래스**
- 해당 필터들은 **서블릿마다 호출**된다.
  (서블릿은 사용자의 요청을 받으면 서블릿을 생성해 메모리에 저장해두고, 같은 클라이언트의 요청을 받으면 생성해둔 서블릿 객체를 재활용하여 요청을 처리한다.)
- ⚠️ **의도치 않은 경우 필터가 두 번씩 적용된다.** Spring Security에서 인증과 인가 또한 Filter로 구현되어 있으므로 영향이 크다.

{% include post-image.html src="filter-double-execution.png" width="1920" height="1080"
   alt="client의 request가 Filter 0 → Filter 1을 지나 API 0에 도달하고, API 0이 API 1으로 redirect하면 다시 Filter 0 → Filter 1을 타게 되는 그림" %}

API 0에서 요청을 처리하고 API 1로 redirect시킬 경우, **클라이언트는 요청을 한 번 한 것뿐이지만 필터를 다시 거치게 된다.**
이 문제를 해결한 것이 `OncePerRequestFilter`다.

> redirect뿐 아니라 `forward`, `include`, 그리고 앞에서 본 **에러 재요청(`/error` dispatch)** 에서도 같은 일이 벌어진다.
> JWT 필터가 두 번 돌면 토큰 파싱도 두 번, 로그도 두 번, DB 조회가 있다면 쿼리도 두 번이다.

### OncePerRequestFilter (추천)

- 모든 서블릿에서 일관된 요청을 처리하기 위해 만들어진 필터, `doFilterInternal` 메서드를 구현한다.
- 이 추상 클래스를 구현한 필터는 **사용자의 요청 하나 당 딱 한 번만 실행**되는 필터를 만들 수 있다.

동작 원리는 단순하다. 내부적으로 `request.setAttribute(alreadyFilteredAttributeName, TRUE)`로 표시를 남기고,
같은 request에서 다시 진입하면 그 attribute를 보고 건너뛴다.

또 하나 유용한 훅으로 `shouldNotFilter()`가 있다. 로그인·회원가입처럼 토큰이 아예 없는 경로는 필터 자체를 건너뛸 수 있다.

```java
@Override
protected boolean shouldNotFilter(HttpServletRequest request) {
    String path = request.getRequestURI();
    return path.startsWith("/auth/") || path.startsWith("/swagger-ui/");
}
```

## 2-3. JWT Authentication Filter 동작 과정

1. `OncePerRequestFilter`를 상속받고 `doFilterInternal` 메서드를 오버라이드한다.
   이때 파라미터로 `HttpServletRequest`, `HttpServletResponse`, `FilterChain`을 받는다.
2. `HttpServletRequest`에서 **Header 정보**를 깐다.
3. 해당 Request Header가 `"Bearer {Token}"` 형태인지 확인하고,
   `"Bearer "` 부분은 제거하여 Base64 형태로 인코딩되어 있는 `{Token}` 문자열을 꺼낸다.
4. `{Token}` 문자열이 비어있지는 않았는지, 만료되거나 위조되지 않았는지 **Token을 검증**하고,
   정상적인 토큰일 경우 해당 토큰의 Payload를 파싱하여 `Authentication`(인증) 객체를 만들고 **`SecurityContext`에 저장**한다.
5. `FilterChain`의 `doFilter` 메서드로 `HttpServletRequest`와 `HttpServletResponse`를 전달한다.

```java
@Component
@RequiredArgsConstructor
public class JwtAuthenticationFilter extends OncePerRequestFilter {

    private final TokenProvider tokenProvider;

    @Override
    protected void doFilterInternal(
            HttpServletRequest request, HttpServletResponse response, FilterChain filterChain)
            throws ServletException, IOException {
        String token = resolveToken(request);

        if (StringUtils.hasText(token) && tokenProvider.isAccessToken(token)) {
            Authentication authentication = getAuthentication(token);
            SecurityContextHolder.getContext().setAuthentication(authentication);
        }

        filterChain.doFilter(request, response);
    }

    public String resolveToken(HttpServletRequest request) {
        String bearerToken = request.getHeader(HttpHeaders.AUTHORIZATION);
        if (StringUtils.hasText(bearerToken) && bearerToken.startsWith(BEARER)) {
            return bearerToken.substring(7);
        }
        return null;
    }

    public Authentication getAuthentication(String token) {
        AccessTokenInfo accessTokenInfo = tokenProvider.parseAccessToken(token);

        AuthUserDetails userDetails = new AuthUserDetails(
                accessTokenInfo.userId(), accessTokenInfo.role());
        return new UsernamePasswordAuthenticationToken(
                userDetails, null, userDetails.getAuthorities());
    }
}
```

> 📌 `UsernamePasswordAuthenticationToken`의 **3-arg 생성자**(principal, credentials, authorities)를 쓰면
> 내부적으로 `setAuthenticated(true)`가 호출된다. 2-arg 생성자는 `authenticated = false`인 "인증 요청용" 토큰이라
> 여기서 쓰면 인증된 유저로 인식되지 않는다.
> 그리고 `credentials`에는 이미 토큰으로 인증을 끝냈으므로 `null`을 넣는다.

## 2-4. ‼️ 기껏 만든 커스텀 필터, SecurityConfig에서 실제 필터 구조 사이에 끼워넣어야 동작하겠죠?

```java
http
    .addFilterBefore(jwtAuthenticationFilter, UsernamePasswordAuthenticationFilter.class)
```

필터를 `@Component`로 빈 등록만 해두면 Security 필터 체인이 아니라 **서블릿 컨테이너의 필터**로 등록되어
엉뚱한 순서로 돌 수 있다. 반드시 `HttpSecurity`에 위치를 지정해서 끼워넣어야 한다.

`UsernamePasswordAuthenticationFilter` 앞에 두는 이유는, 폼 로그인 필터가 인증을 시도하기 전에
이미 JWT로 `SecurityContext`를 채워두기 위해서다.

## 2-5. 🛠️ UserDetails 구현하기

```java
@Getter
@AllArgsConstructor
public class CustomUserDetails implements UserDetails {

    private Long userId;

    private Role role;

    @Override
    public Collection<? extends GrantedAuthority> getAuthorities() {
        return Collections.singletonList(
                new SimpleGrantedAuthority("ROLE_" + role.getStringValue())
        );
    }

    @Override
    // .. //
}
```

> ⚠️ **`ROLE_` 접두사**는 관례가 아니라 실제 동작에 관여한다.
> `@PreAuthorize("hasRole('ADMIN')")`은 내부에서 `ROLE_ADMIN` 권한을 찾는다.
> 반면 `hasAuthority('ROLE_ADMIN')`은 접두사를 붙이지 않고 문자열 그대로 비교한다.
> 위 코드처럼 `"ROLE_" + role`로 저장했다면 `hasRole('ADMIN')` / `hasAuthority('ROLE_ADMIN')` 둘 다 통과한다.

나머지 오버라이드 메서드(`isAccountNonExpired`, `isAccountNonLocked`, `isCredentialsNonExpired`, `isEnabled`)는
계정 상태 정책을 쓰지 않는다면 `true`를 반환하면 된다. **기본값이 `false`로 남으면 인증이 조용히 실패**하므로 주의하자.. ..

## 2-6. 번외) Spring Security 로그인 기능을 활용한다면?

JWT만 쓰면 `UserDetailsService`는 사실상 안 써도 되지만, 폼 로그인/`AuthenticationManager`를 쓴다면 흐름은 이렇다.

1. `UserDetailsService`의 `loadUserByUsername()` 호출
2. DB에서 사용자 조회
3. `UserDetails` 반환
4. `PasswordEncoder`로 비밀번호 비교
5. 성공하면 `Authentication` 생성

```java
@Service
@RequiredArgsConstructor
public class CustomUserDetailsService implements UserDetailsService {

    private final UserAdaptor userAdaptor;
    private final PasswordEncoder passwordEncoder;

    @Override
    public AuthUserDetails loadUserByUsername(String username) throws UsernameNotFoundException {
        return userAdaptor.findArtistUserIdAndRoleByLoginId(username);
    }

    public boolean userLogin(String loginId, String password) {
        User artistUser = userAdaptor.findArtistUserByLoginId(loginId);

        if (!passwordEncoder.matches(password, artistUser.getPassword())) {
            throw new IllegalArgumentException("비밀번호 불일치");
        }

        return true;
    }
}
```

# 3. 본격 트러블슈팅 — 익명 유저가 401이 아니라 403을 받는다

본 프로젝트에 들어오면서, 첫 인식은 **Security Filter가 아니라 `@PreAuthorize`를 이용해서 개별 API의 권한 제어를 하는 게 목표**였다.
(서로 다른 동작이 아닐 것으로 기대했다.)

결론부터 말하면 **서로 다른 동작이었다.**

## 3-1. Security 관련 Filter Layer 정리

```
(초반 공통 필터들)
  ↓
CorsFilter                            ✅ corsConfigurationSource()로 동작
  ↓
CsrfFilter                            ❌ 비활성화 (csrf.disable)
  ↓
... (기타 기본 필터들)
  ↓
JwtAuthenticationFilter               ✅ addFilterBefore(…, UsernamePasswordAuthenticationFilter)
  ↓
UsernamePasswordAuthenticationFilter  (폼로그인용, JWT만 쓰면 사실상 의미 적음)
  ↓
AnonymousAuthenticationFilter         ❌ 비활성화 (anonymous().disable)
  ↓
ExceptionTranslationFilter            ✅ 예외를 401/403으로 "번역"하는 핵심
  ├─ AuthenticationException  → authenticationEntryPoint (401)
  └─ AccessDeniedException    → accessDeniedHandler      (403)
  ↓
AuthorizationFilter                   ✅ authorizeHttpRequests: anyRequest().permitAll()이라 "거의 통과"
  ↓
(통과하면)
DispatcherServlet → Controller
```

여기서 주인공은 **`ExceptionTranslationFilter`** 다.
이 필터는 자기 **아래(뒤)** 에서 발생한 예외를 `try/catch`로 잡아 HTTP 상태 코드로 번역한다.
바꿔 말하면, **이 필터에 예외가 도달해야만** 내가 등록한 `authenticationEntryPoint` / `accessDeniedHandler`가 호출된다.

## 3-2. `@PreAuthorize`는 어디서 동작하나

- 필터 이후, 컨트롤러 **직전** 레이어에서 권한 에러 발생을 감지한다.
- 이때, 앞서 `SecurityContextHolder`에 인증된 유저를 기반으로 제어한다.

정확히는 `HandlerInterceptor`가 아니라 **Spring AOP 프록시**다.
`@EnableMethodSecurity`가 켜지면 대상 빈(컨트롤러/서비스)에 프록시가 씌워지고,
메서드 호출 순간 `AuthorizationManagerBeforeMethodInterceptor`가 SpEL 표현식을 평가한다.
그래서 위치상으로는 "DispatcherServlet 안쪽, 컨트롤러 메서드 진입 직전"이다.

## 3-3. 문제의 발생 — anonymous가 켜져 있으면

- Security Filter에서 **토큰이 없거나 잘못된 토큰**이 들어온 상황에서
  anonymous user로 authentication을 세팅하도록 지정되어 있다면 **(default setting에 해당)**, 인증은 된 유저로 인식한다.
- 이에 `@PreAuthorize("isAuthenticated()")`가 걸려 있는 메서드여도 **403 Forbidden**이 발생한다.
  정확히는 `AccessDeniedException`의 발생으로 403 에러에 해당한다.
- 즉 **"로그인은 했는데, 해당 컨트롤러 메서드에 접근 권한이 없음"** 으로 인식된 것이다.

Anonymous Filter를 켠 상태에서 authentication에 어떻게 설정되는지 로그로 확인한 결과:

```
Current Authentication:
AnonymousAuthenticationToken [Principal=anonymousUser, Credentials=[PROTECTED],
Authenticated=true, Details=WebAuthenticationDetails [RemoteIpAddress=127.0.0.1,
SessionId=null], Granted Authorities=[ROLE_ANONYMOUS]]
```

- `Authenticated=true`가 설정되어 있음을 확인할 수 있다.
- 이로 인해 `@PreAuthorize("isAuthenticated()")`가 걸려 있는 메서드도 **Authentication이 존재한다는 이유로 401이 아닌 403**으로 exception이 터진다.

> `isAuthenticated()`가 `true`를 반환하지 않는 이유가 헷갈릴 수 있다.
> Spring Security의 SpEL `isAuthenticated()`는 단순히 `authentication.isAuthenticated()`를 보는 게 아니라
> **`AuthenticationTrustResolver`로 익명 여부를 먼저 판별**한다. 익명이면 `false`.
> 그래서 "인증 객체는 존재하지만 익명" → 표현식은 실패 → `AccessDeniedException`(403)이라는,
> 딱 최악의 조합이 만들어진다.

## 3-4. 해결 시도 — anonymous를 꺼보자

⇒ 이를 해결하기 위해 anonymous user 설정을 security 설정에서 꺼주면 될까?

```java
@Bean
public SecurityFilterChain securityFilterChain(
    HttpSecurity http
) throws Exception {

    http
        .csrf(csrf -> csrf.disable())
        .cors(cors -> cors.configurationSource(corsConfigurationSource()))
        .anonymous(AbstractHttpConfigurer::disable) // anonymous 세팅 비활성화
        .authorizeHttpRequests(auth -> auth
            .anyRequest().permitAll()
        )
        .exceptionHandling(ex -> ex
                .authenticationEntryPoint(authenticationEntryPoint)
                .accessDeniedHandler(accessDeniedHandler)
        )
        .addFilterBefore(jwtAuthenticationFilter, UsernamePasswordAuthenticationFilter.class)
    ;

    return http.build();
}
```

anonymous를 끄면 `SecurityContext`의 `Authentication`이 **`null`** 이 된다.
이 상태에서 `@PreAuthorize`가 걸린 메서드를 호출하면 메서드 시큐리티는 `AccessDeniedException`이 아니라
**`AuthenticationCredentialsNotFoundException`** 을 던진다. 이건 `AuthenticationException`의 하위 타입이므로,
`ExceptionTranslationFilter`까지 도달하기만 하면 `authenticationEntryPoint` → **401**로 번역된다.

즉 의도한 방향은 맞다. 그런데 여기서 **두 번째 벽**을 만났다.

## 3-5. 진짜 원인 — GlobalExceptionHandler가 먼저 잡아먹는다

```
FilterChainProxy
  ↓
... (여러 필터)
  ↓
ExceptionTranslationFilter  ← 여기서 try/catch로 아래를 감쌈
  ↓
DispatcherServlet
  ↓
Controller
  ↓
(AOP) @PreAuthorize 검사
  ↓
예외 던짐(AccessDeniedException 403 / AuthenticationException 401)
  ↑ (콜스택 unwind)
ExceptionTranslationFilter가 잡음
  ├─ AuthenticationException → AuthenticationEntryPoint → 401
  └─ AccessDeniedException   → AccessDeniedHandler      → 403
```

이론상 위 그림대로 흘러야 한다. 그런데 실제로는 **`GlobalExceptionHandler`에 의해 에러 핸들링이 일어났다.**

이유는 이렇다.
`@PreAuthorize`에 의한 권한 에러는 **필터가 아니라 그보다 안쪽(컨트롤러 메서드 진입 지점)에서 발생**한다.
Security Filter에 지정되어 있는 `AccessDeniedHandler`로 처리되려면 예외가 필터까지 **전파**되어야 하는데,
그 전에 Advice에 해당하는 `@RestControllerAdvice` GlobalExceptionHandler가 이미 예외를 잡아 응답을 만들어버린다.
**응답이 이미 커밋되었으므로 상위 filter까지 에러가 전파되지 않는다.**

정리하면 순서는 이렇다.

```
@PreAuthorize → AccessDeniedException 발생
   ↓
DispatcherServlet의 HandlerExceptionResolver가 catch
   ↓
ExceptionHandlerExceptionResolver → @RestControllerAdvice 매칭
   ↓
GlobalExceptionHandler가 403 JSON 응답 작성 ✅ (여기서 종료)
   ↓
❌ ExceptionTranslationFilter는 아무 예외도 못 봄 → accessDeniedHandler 미호출
```

### 해결책

`GlobalExceptionHandler`에서 Security 예외를 **잡지 않거나, 잡았으면 다시 던져야** 한다.

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    // ❌ 이렇게 하면 Security의 accessDeniedHandler가 영원히 호출되지 않는다
    // @ExceptionHandler(AccessDeniedException.class)
    // public ResponseEntity<?> handle(AccessDeniedException e) { ... }

    // ✅ Security 예외는 그대로 통과시켜 ExceptionTranslationFilter가 처리하게 한다
    @ExceptionHandler({AccessDeniedException.class, AuthenticationException.class})
    public void rethrow(RuntimeException e) throws Exception {
        throw e;
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponse> handle(Exception e) { /* ... */ }
}
```

`@ExceptionHandler(Exception.class)` 같은 **광범위한 핸들러 하나**가
Security 예외까지 싹 쓸어담고 있는 경우가 대부분이므로, 이 지점을 먼저 의심하면 된다.

> 하나 더. anonymous를 **켜둔 채로** 예외를 `ExceptionTranslationFilter`까지 전파시키면
> 이 필터는 `AuthenticationTrustResolver`로 "익명 유저의 AccessDenied"임을 판별하고,
> `accessDeniedHandler`가 아니라 **`authenticationEntryPoint`(401)로 보낸다.**
> 즉 예외 전파만 제대로 뚫어주면 anonymous를 굳이 끄지 않아도 401을 받을 수 있다.
> 어느 쪽을 택하든, 핵심은 **"예외가 필터까지 도달하는가"** 다.

# 4. 남은 과제

여기까지 오면 401/403은 해결되나, 다른 문제가 남게 된다.

- `@PreAuthorize`만을 사용해서는 **JWT 토큰에 어떤 문제가 있었는지 응답에 반환할 수가 없다.**
- 프론트 측에서 최대한 자세한 로그를 반환해주길 원했으므로 **토큰 만료 / 유효하지 않은 토큰 형식** 등을 구분해서 내려줘야 하는데, 이것이 어려운 상황.
- 따라서 JWT 토큰의 문제를 지적하기 위해서는 **Security Filter에서 토큰의 유효성 검증이 일어날 때 애초에 에러 핸들링이 일어나길** 기대한다.
- 즉 `JwtAuthenticationFilter`에서 token 유효성을 검증할 때 에러 반환을 해야 한다.
- 에러를 받아서 처리하는 주체는 `accessDeniedHandler`(또는 `authenticationEntryPoint`)가 되길 기대하는데, 이후 구현은 고민 중에 있다 !

근본 원인은 앞의 필터 코드에 있다.

```java
if (StringUtils.hasText(token) && tokenProvider.isAccessToken(token)) {
    // 유효할 때만 인증 세팅
}
// 유효하지 않으면? 아무 일도 없이 그냥 통과 → "왜 실패했는지" 정보가 소실된다
```

토큰이 만료됐든, 서명이 깨졌든, 형식이 이상하든 **결과가 전부 "인증 없음" 하나로 뭉개진다.**
현재 검토 중인 선택지는 두 가지다.

## 방안 A. Request attribute에 실패 사유를 실어 EntryPoint로 넘기기

```java
@Override
protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                FilterChain filterChain) throws ServletException, IOException {
    String token = resolveToken(request);
    try {
        if (StringUtils.hasText(token)) {
            SecurityContextHolder.getContext().setAuthentication(getAuthentication(token));
        }
    } catch (ExpiredJwtException e) {
        request.setAttribute("authErrorCode", ErrorCode.EXPIRED_TOKEN);
    } catch (JwtException | IllegalArgumentException e) {
        request.setAttribute("authErrorCode", ErrorCode.INVALID_TOKEN);
    }
    filterChain.doFilter(request, response);   // 판단은 뒤로 미룬다
}
```

```java
@Component
public class CustomAuthenticationEntryPoint implements AuthenticationEntryPoint {
    @Override
    public void commence(HttpServletRequest request, HttpServletResponse response,
                         AuthenticationException authException) throws IOException {
        ErrorCode code = (ErrorCode) request.getAttribute("authErrorCode");
        if (code == null) code = ErrorCode.UNAUTHORIZED;
        // 401 + 상세 코드 JSON 작성
    }
}
```

- **장점**: 응답 작성 지점이 `EntryPoint` 한 곳으로 모여 포맷이 일관된다. 필터는 판단만 하고 응답은 만들지 않는다.
- **단점**: attribute를 매개로 한 암묵적 결합이 생긴다.

## 방안 B. 필터에서 즉시 응답을 써버리기

`ObjectMapper`로 바로 JSON을 쓰고 `filterChain.doFilter()`를 호출하지 않는 방식.

- **장점**: 흐름이 직관적이고 뒤쪽 필터를 아예 태우지 않는다.
- **단점**: 응답 포맷 작성 코드가 필터와 핸들러 양쪽에 중복된다. `HandlerExceptionResolver`를 필터에 주입해 `@RestControllerAdvice`로 위임하는 변형도 가능하다.

지금 기울고 있는 쪽은 **방안 A**다. 응답 포맷을 한 곳에 모을 수 있다는 점이 크다.

# 정리

- **Filter는 스프링 바깥, `@PreAuthorize`는 스프링 안쪽.** 이 경계를 인식하는 게 시작점이다.
- 커스텀 필터는 `OncePerRequestFilter`를 상속하고, `HttpSecurity.addFilterBefore()`로 **체인 안에 끼워넣어야** 동작한다.
- `UsernamePasswordAuthenticationToken`은 **3-arg 생성자**를 써야 `authenticated = true`가 된다.
- anonymous가 켜져 있으면 익명 유저도 `Authenticated=true`라서 `@PreAuthorize("isAuthenticated()")`가 **403**을 뱉는다.
- 그런데 그 403조차 내가 등록한 핸들러가 만든 게 아니었다. **`@RestControllerAdvice`가 예외를 먼저 잡아먹어 `ExceptionTranslationFilter`까지 전파되지 않았기 때문**이다.
- 401/403 문제가 안 풀린다면, 순서대로 확인하자.
  1. `SecurityContext`에 실제로 뭐가 들어있는지 **로그로 찍어본다** (익명인지 `null`인지)
  2. 그 예외가 `ExceptionTranslationFilter`까지 **도달하는지** 확인한다 (GlobalExceptionHandler 의심)
  3. 토큰 실패 사유를 구분해서 내려주고 싶다면, **필터 단계에서 사유를 남겨야** 한다
