[앞 글]({% post_url 2026-10-04-Cura에-Lambda를-도입한다면 %})에서 Cura 백엔드에서 Lambda로 떼어낼 만한 일로 번역·요약 파이프라인, 처방전·검사지 OCR, 예약 작업 세 가지를 꼽았다. 이번 글은 그중 첫 번째인 번역 파이프라인을 실제로 떼어낸 기록이다.

막상 코드를 열어 보니 앞 글에서 전제로 삼은 것 몇 가지가 틀려 있었고, 스레드가 묶일 것이라는 걱정보다 더 구체적인 문제가 이미 코드 안에 있었다. 그래서 그 문제를 로컬에서 재현해 숫자로 확인하고, 번역을 비동기 워커로 옮긴 뒤 같은 조건에서 다시 쟀다. Lambda가 맡을 일을 우선 Spring 안의 워커로 만들고, 그 워커를 그대로 옮긴 Lambda 함수를 SAM으로 실제 AWS 계정에 올리는 데까지 진행했다. 올린 뒤 첫 호출이 어디서 막혔는지도 그대로 적어 둔다. 운영 트래픽을 Lambda로 넘기고 요금을 재는 일은 다음 글에서 다룬다.

## 먼저 바로잡을 사실 세 가지

앞 글은 코드를 보지 않고 머릿속 그림으로 쓴 것이라 실제 코드와 다른 부분이 있었다.

- 번역 API는 Gemini가 아니라 OpenAI다. `OpenAiApiConfig`가 `api.openai.com`에 붙고 모델은 `gpt-4o-mini`를 쓴다. README에도 Gemini라고 적혀 있어서 같이 틀렸다. 설계에는 영향이 없다.
- 파일 업로드와 OCR은 아직 없다. `MultipartFile`을 받는 코드가 한 군데도 없다. 앞 글에서 2번으로 꼽은 OCR은 떼어낼 대상이 아니라 새로 만들어야 하는 기능이다.
- 번역은 보고서를 만들 때가 아니라 수정할 때만 돈다. 통번역가가 보고서를 저장(`PUT /consultations/{id}`)하면 환자 모국어로 적힌 항목을 한국어로 번역해 `translated_*` 컬럼에 넣는다.

정리하면 이번 글에서 다루는 대상은 보고서 저장 요청 안에서 동기로 돌던 OpenAI 호출 하나다.

## 지금 코드가 막히는 방식

앞 글에서는 외부 API 응답을 기다리는 동안 톰캣 스레드가 묶인다고 썼다. 그 말 자체는 맞지만, Cura에서 먼저 바닥나는 것은 스레드가 아니라 DB 커넥션이었다.

`ConsultationService.update()`에는 `@Transactional`이 붙어 있고, 그 안에서 `TranslationService.translateToKorean()`을 동기로 호출한다. 트랜잭션이 열려 있는 동안에는 Hikari 커넥션 하나를 계속 쥐고 있게 된다. 운영 설정의 풀 크기는 5인데, Supabase 무료 티어가 PgBouncer 뒤에서 서버 커넥션 60개를 여러 클라이언트가 나눠 쓰는 구조라 일부러 작게 잡아 둔 값이다.

여기에 한 가지가 더 겹친다. 번역이 끝나면 진료 내용이 국외(OpenAI)로 이전됐다는 감사기록을 `AuditService.recordThirdPartyTransfer()`로 남기는데, 이 메서드의 전파 속성이 `REQUIRES_NEW`다. 감사기록은 본 트랜잭션이 롤백돼도 남아야 하므로 맞는 선택이다. 문제는 `REQUIRES_NEW`가 첫 커넥션을 쥔 채로 두 번째 커넥션을 요구한다는 점이다.

저장 요청이 동시에 5개 들어오면 이렇게 흘러간다.

1. 요청 5개가 커넥션을 하나씩 잡고 각자 OpenAI 응답을 기다린다. 이 시점에 풀은 비어 있다.
2. 3초 뒤 번역이 돌아오면 5개 요청이 각자 감사기록용 두 번째 커넥션을 요청한다.
3. 남은 커넥션이 없으므로 5개 요청이 서로 커넥션을 놓아주기를 기다린다. 아무도 먼저 놓을 수 없다.
4. `connection-timeout`(운영 10초, 로컬 기본 30초)이 지나면 예외가 난다. 그 사이에 들어온 로그인, 목록 조회 같은 다른 요청도 전부 같이 기다린다.

풀 크기만큼의 동시 저장만으로 서버 전체가 멈추는 교착이다. 동시 저장이 4건까지는 멀쩡하고 5건째부터 터진다.

### 재현

로컬에서 운영과 같은 조건을 만들었다. Postgres는 Docker로 띄우고 Hikari 풀은 5로 맞췄다. OpenAI 자리에는 3초를 기다렸다가 응답하는 대역 서버를 두었다. 통번역가 토큰으로 보고서 저장을 동시에 N건 보내면서, 150ms 간격으로 번역과 무관한 조회 요청을 같이 보내 다른 사용자가 겪는 응답 시간을 쟀다.

| 동시 저장 | 저장 응답 p50 | 그동안 무관한 GET p50 | OpenAI 실제 호출 | 결과 |
|---|---|---|---|---|
| 4건 | 3.1초 | 27ms | 4 | 정상 |
| 5건 | 33.1초 | 2.8초 | 5 | 전부 30초 대기 후 응답 |
| 20건 | 33.1초 | 30.1초 (1건만 돌아옴) | 5 | 15건 500/403, 5건은 33초 뒤 응답 |

20건을 보냈는데 OpenAI 호출은 5번뿐이다. 나머지 15건은 OpenAI 근처에도 가지 못하고 커넥션을 기다리다 실패했다. 로그에는 같은 줄이 반복된다.

```
HikariPool-1 - Connection is not available, request timed out after 30008ms (total=5, active=5, idle=0, waiting=20)
```

브라우저에서는 이렇게 보인다. 저장 20건이 몰린 동안 다른 사용자가 목록 화면을 열면 스피너가 31.9초 동안 돈다.

## 어떻게 바꿨나

원칙은 앞 글에서 정한 그대로다. 저장은 즉시 돌려주고, 기다리는 일은 다른 곳에서 한다. 다만 그 다른 곳을 처음부터 Lambda로 두지 않고, 같은 JVM 안에서 도는 작은 워커로 먼저 만들었다. 상태 컬럼, 멱등성, 폴링 같은 비동기 계약을 Spring 안에서 먼저 확정해 두면 2단계에서는 워커가 어디서 도는지만 바뀐다.

### 상태 컬럼과 버전

```sql
ALTER TABLE consultation
    ADD COLUMN translation_status  VARCHAR(16) NOT NULL DEFAULT 'NONE',   -- NONE | PENDING | DONE | FAILED
    ADD COLUMN translation_version BIGINT      NOT NULL DEFAULT 0;
```

`translation_version`은 저장할 때마다 1씩 오른다. 워커는 자기가 받은 버전과 현재 버전이 같을 때만 결과를 쓴다. 이 번호로 두 가지 문제를 같이 막는다. 하나는 SQS가 최소 1회 전달이라 같은 작업이 두 번 오는 경우고, 다른 하나는 번역이 돌아오기 전에 사용자가 다시 저장해서 원문이 바뀐 경우다. 둘 다 옛 버전의 결과이므로 버리면 된다.

### 요청 쪽

`update()`는 이제 OpenAI를 직접 호출하지 않는다. 번역이 필요하면 상태를 `PENDING`으로 표시만 하고, 작업(진료기록 id, 버전, 요청자)을 커밋이 끝난 뒤에 디스패처로 넘긴다.

```java
TranslationJob job = requestTranslationIfNeeded(c, principal);   // status=PENDING, version++
Consultation updated = consultationRepository.save(c);
dispatchAfterCommit(job);                                        // TransactionSynchronization.afterCommit
return ConsultationResponse.Detail.from(updated, ...);
```

커밋 전에 넘기면 워커가 아직 커밋되지 않은 옛 원문을 읽을 수 있다. `TransactionSynchronizationManager.registerSynchronization()`의 `afterCommit`에 걸어 두면 커밋이 끝난 뒤에만 호출된다.

### 워커 쪽

워커는 트랜잭션을 직접 열지 않는다. 열어 두면 OpenAI를 기다리는 동안 다시 커넥션을 쥐게 되기 때문이다. 대신 DB 접근을 짧은 트랜잭션 세 개로 쪼갰다.

```
loadPending(job)   읽기 트랜잭션: 버전 확인 → 원문 읽기 → 가명처리 → 커넥션 반납
translateToKorean  커넥션 없음:   OpenAI 호출 (3초)
complete(job, t)   쓰기 트랜잭션: 버전이 아직 같으면 translated_* 와 DONE 기록 → 반납
recordThirdParty   REQUIRES_NEW:  감사기록 (이제 밖에서 쥔 커넥션이 없으니 교착이 없다)
```

워커 스레드에는 `SecurityContext`가 없어서 감사기록의 주체를 알 수 없다. 그래서 작업에 요청자의 id와 역할을 함께 실어 보낸다. 실명 가명처리(`PiiScrubber`)는 읽기 트랜잭션 안에서 끝내고, 그 뒤로는 가명처리된 텍스트만 다니게 했다.

워커 스레드 풀은 2개로 잡았다. 이 숫자가 OpenAI 동시 호출 상한이면서, 번역이 잠깐씩 빌리는 커넥션 수의 상한이기도 하다. Lambda로 옮기면 예약 동시성(reserved concurrency)이 같은 역할을 한다.

### 화면 쪽

저장 응답에 `translationStatus`가 실린다. 값이 `PENDING`이면 1.5초 간격으로 `GET /consultations/{id}`를 다시 불러 `DONE`이 될 때까지 기다리고, 그동안 "한국어 번역 중…" 배지를 보여준다. 번역본은 `DONE`일 때만 보여준다. `PENDING`이나 `FAILED` 상태에서 이전 번역을 그대로 보여주면 지금 원문과 다른 내용이 나란히 놓이기 때문이다.

### 테스트로 못 박은 것

비동기로 바꾸면 "되는 것 같다"에서 끝내기 쉬워서 다섯 가지를 테스트로 고정했다.

1. 저장은 `PENDING`으로 즉시 돌아오고, 뒤에서 `DONE`이 된다.
2. 같은 작업이 두 번 와도 OpenAI는 한 번만 불린다.
3. 번역 중에 원문이 다시 저장되면 옛 버전 결과는 버려지고 새 원문의 번역만 남는다.
4. 외부 호출이 실패하면 `FAILED`로 남고 원문은 그대로다.
5. 번역이 꺼져 있으면 `PENDING`으로 표시하지 않는다.

이 중 3번이 가장 중요하다. 첫 번역이 OpenAI를 기다리는 사이에 두 번째 저장을 넣고, 첫 번역이 돌아왔을 때 버전 불일치로 버려지는지 확인한다.

## 2단계: 같은 워커를 Lambda로

워커를 Spring 안에 두는 것만으로도 교착은 풀렸다. 그래도 Lambda로 옮기려는 이유는 앞 글과 같다. 번역 동시성 상한을 Spring의 커넥션 풀과 분리하고, OpenAI 키를 Spring에서 치우고, 몰릴 때만 늘어나는 비용 곡선을 갖기 위해서다.

이번에 준비한 것은 세 가지다.

첫째는 디스패처 인터페이스다. `TranslationJobDispatcher` 구현이 둘인데, 기본은 스레드 풀(`async`)이고 `byby.translation.dispatcher=sqs`로 바꾸면 `SqsTranslationJobDispatcher`가 SQS에 `{consultationId, version, requestedBy, requestedRole}`만 발행한다. 환자 원문은 싣지 않는다. 큐, DLQ, CloudWatch 어디에도 진료 내용이 남지 않게 하기 위해서다.

둘째는 Lambda 함수(`lambda/translation/src/handler.py`)다. Spring 워커의 네 단계를 Python으로 옮겼다. Init 단계에서 SSM 파라미터와 DB 커넥션을 한 번 만들어 환경이 재사용되는 동안 같이 쓴다. Supabase 풀러(6543, transaction mode)로 붙으므로 `prepare_threshold=None`으로 prepared statement를 끈다. 가명처리는 `PiiScrubber.java`를 그대로 옮긴 `pii.py`가 맡는다. 쓰기는 `UPDATE ... WHERE id = ? AND translation_version = ?`로 하고, 영향받은 행이 0이면 결과를 버린다.

셋째는 SAM 템플릿(`lambda/translation/template.yaml`)이다. 큐와 DLQ(3회 실패 후 이동, 14일 보관), 함수(arm64, 256MB, 예약 동시성 5), 함수 역할(자기 큐와 SSM 파라미터 2개만), 로그 보존 30일, 그리고 Railway 쪽 IAM 사용자에 붙일 `sqs:SendMessage` 전용 정책이 들어 있다. VPC 설정은 넣지 않았다. NAT Gateway를 피하기로 한 앞 글의 결론 그대로다.

AWS 없이 이 함수를 로컬 Postgres와 OpenAI 대역 서버로 돌려봤다. 같은 메시지 두 개와 한 버전 낮은 메시지 하나를 한 배치에 넣었다.

```
INFO 완료 id=1d3e3027-… v=1 applied=True openai_ms=3060
INFO 버전 불일치로 건너뜀 id=1d3e3027-… job.v=0 current.v=1
result: {'batchItemFailures': []}
row: ('DONE', 1, '(한국어 번역) Toi ten la [이름], so [연락처]. Dau bung.')
audit: 수신자=OpenAI API (국외) / 목적=진료내용 한국어 번역 / 가명처리 적용 / 원어=vi / Lambda 워커 / 반영=Y
```

OpenAI는 한 번만 호출됐고, 중복 메시지는 이미 `DONE`이라 건너뛰었고, 옛 버전은 버전 불일치로 건너뛰었다. 이름과 전화번호는 외부로 나가기 전에 치환됐고 감사기록도 남았다. OpenAI 주소를 닫힌 포트로 바꿔 돌리면 해당 메시지만 `batchItemFailures`로 돌려보내고 행은 `FAILED`가 된다.

## 실제로 올려 보기

템플릿을 AWS에 올렸다. 계정이 소셜 로그인으로 만드는 "새 AWS 경험" 프로젝트라서 앞 글에서 가정한 것과 다른 점이 몇 가지 있었다.

- 리전이 고정돼 있다. 프로젝트가 `ap-southeast-2`(시드니)에 만들어져 있고 다른 리전에는 리소스를 만들 수 없다. 앞 글에서 Supabase와 Lambda를 같은 리전(서울)에 두겠다고 했는데 이 계정에서는 불가능하다. 함수는 시드니, DB는 서울에 있게 됐다. 영향은 아래 숫자로 확인했다.
- 액세스 키가 없다. `aws login`으로 브라우저 로그인을 하면 12시간짜리 자격증명이 생기고 90일 동안 갱신된다. 배포 자격증명을 어디에 저장할지 고민할 일이 없어졌다.
- 무료 플랜에 $100 크레딧이 있다. Lambda, SQS, SSM, CloudFormation은 모두 무료 구간 안에서 돌았다.

배포는 세 명령으로 끝난다.

```
sam build --use-container                   # psycopg 바이너리를 Lambda arm64용으로 컨테이너 안에서 빌드
sam package --resolve-s3                    # 코드 zip을 S3에 올리고 CodeUri를 치환한 템플릿 생성
aws cloudformation execute-change-set ...   # 변경 세트를 먼저 만들어 검토하고 실행
```

`--use-container`는 빼먹기 쉬운데, 빼면 Windows용 wheel이 들어가서 Lambda에서 import가 실패한다. 변경 세트는 생성될 리소스 7개(큐 2, 함수, 실행 역할, 이벤트 소스 매핑, 로그 그룹, 발행용 정책)가 템플릿과 같은지 보고 실행했다. 비밀 두 개(Supabase 풀러 주소, OpenAI 키)는 SSM Parameter Store에 SecureString으로 넣었다. 함수 역할은 그 파라미터 두 개와 자기 큐만 읽을 수 있다.

### 첫 호출

존재하지 않는 진료기록 id를 큐에 넣어 봤다. 함수가 DB에 붙어 조회까지 하고 해당 행이 없다는 결과로 끝나면 연결 경로 전체가 검증되고, 데이터는 건드리지 않는다.

```
INIT_START  Runtime Version: python:3.12 ...
REPORT  Duration: 1553 ms  Billed Duration: 2240 ms  Memory Size: 256 MB  Max Memory Used: 119 MB  Init Duration: 686 ms
[ERROR] psycopg.errors.UndefinedColumn: column c.translation_status does not exist
```

여기서 세 가지를 알 수 있다.

1. 콜드 스타트가 686ms다. Python 런타임 기동, SSM 파라미터 2개 조회, Supabase 풀러 TLS 연결까지 포함한 시간이다. 앞 글에서 JVM은 수 초가 걸린다고 했는데, Python으로 만든 덕을 여기서 봤다.
2. 시드니와 서울 사이 왕복을 포함해 호출 한 번에 1.5초가 걸렸다. 걱정했던 IPv6 문제는 없었다. Supabase 대시보드가 풀러는 IPv6가 기본이라고 경고하지만 공유 풀러는 IPv4로도 붙었다.
3. 실패 원인은 AWS 쪽이 아니라 DB 스키마다. `translation_status` 컬럼이 운영 DB에 없다. V21 마이그레이션은 Spring이 기동하면서 Flyway로 적용하는데, Spring 쪽 변경이 아직 운영에 배포되지 않았다. 워커를 먼저 올리고 스키마를 나중에 올린 순서가 잘못됐다.

당연한 이야기지만 직접 겪고 나니 분명해졌다. 2단계는 1단계가 운영에 올라간 뒤에만 켤 수 있다. 순서는 Spring 배포(V21 적용, 워커는 아직 Spring 안)를 먼저 하고, Railway에 `TRANSLATION_DISPATCHER=sqs`와 큐 URL, 발행 자격증명을 추가한 뒤 재배포하는 것이다. 디스패처를 설정값으로 고를 수 있게 만든 것이 여기서 쓸모가 있다. 되돌릴 때도 변수 하나만 바꾸면 된다.

테스트 메시지는 큐에서 지웠다. 두면 3번 재시도한 뒤 DLQ에 가짜 메시지가 남는다.

## 정리

- 앞 글에서 걱정한 스레드 고갈은 Cura에서는 커넥션 고갈이었다. `REQUIRES_NEW` 감사기록 때문에 풀 크기(5)만큼의 동시 저장으로 서버 전체가 교착했다.
- 번역을 커밋 뒤 워커로 빼자 저장 응답이 33초에서 89ms가 됐고, 20건이 몰려도 다른 요청은 영향을 받지 않는다.
- 상태 컬럼과 버전 번호로 멱등성을 만들었다. 중복 메시지와 처리 중 재저장 모두 테스트로 고정했다.
- 감사기록과 가명처리는 워커로 같이 옮겼다. 큐에는 id와 버전만 실린다.
- 같은 워커를 Python으로 옮긴 Lambda와 SAM 템플릿을 로컬에서 멱등성, 가명처리, 실패 경로까지 확인한 뒤 실제로 올렸다. 콜드 스타트는 686ms, 시드니에서 서울 DB까지 포함한 호출은 1.5초였다.
- 워커보다 스키마가 먼저다. 2단계 전환은 Spring 배포 뒤에 설정값 하나로 켠다.

다음 글에서는 Spring을 배포해 운영 트래픽을 Lambda로 넘기고, Railway 쪽에 `sqs:SendMessage` 전용 자격증명을 두고, 한 달 요금을 재 볼 생각이다. README의 Gemini도 OpenAI로 고친다.
